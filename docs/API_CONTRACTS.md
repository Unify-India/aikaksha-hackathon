# MCP Tool Contracts — Abhyas Voice Exam POC

**Source baseline:** `ABHYAS_VOICE_EXAM_SPEC.md`. **Implementation status:** proposed until repository inspection.

## Trust boundary

All tools run for an authenticated principal. Derive `teacherId` and tenant/institute scope from a verified token/session and server-side mapping. Never accept `teacherId`, tenant ID, raw database path, arbitrary URL, API key or role as trusted caller input. Every read/write checks teacher ownership and tenant scope.

## Tool 1 — `resolve_teacher_context`

Input: none.  
Output (bounded): authorized teacher display context, batches `{id,name,subject,classLevel}`, recent exams and available syllabus/topic references where implemented. Do not expose API keys or unrestricted user profile data. Batch fuzzy matching belongs in orchestration; if zero or multiple candidates remain, ask a clarifying question.

## Tool 2 — `create_exam`

Input (normalized DTO; required values validated server-side):

```json
{
  "title": "NEET Electrostatics Quiz",
  "batchId": "opaque-authorized-batch-ref",
  "duration": 45,
  "targetQuestions": 15,
  "defaultMarks": 4,
  "negativeRule": "1/4",
  "date": "YYYY-MM-DD",
  "startTime": "10:00",
  "endTime": "10:45",
  "languages": ["en"],
  "isSubjective": false
}
```

Output: `{ "examId": "opaque-exam-ref", "status": "draft" }`.  
The service validates batch ownership, duration/count/marks, language, date/time, timezone and schedule invariants. Do not silently resolve conflicting duration/end time. Idempotency key is required at transport/service boundary even if omitted from the source's illustrative JSON.

## Tool 3 — `generate_and_attach_questions`

Input: `{examId, subject, topic, subtopic?, count, difficulty, languages, guidelines?}`. `count` is 1–15 per generation call; orchestrator may make bounded sequential calls for larger totals if product scope later permits. Verify exam ownership and draft state.

Output should include `{generatedCount, requestedCount, validationStatus, warnings, questionPreview, operationRef}`. Keep correct answers/explanations in trusted server memory or protected answer-key persistence; never return them in a client-visible MCP result unless the authenticated teacher experience explicitly needs them and authorization is enforced. Normalize `A`–`D` to the Abhyas option IDs only after inspecting actual model. Persist/attach through existing Abhyas server-side service, not direct guessed database writes.

## Tool 4 — `finalize_and_publish_exam`

Source input: `{examId,status:"upcoming"}`. POC-safe input extends it with a server-issued `confirmationRef` and `idempotencyKey`. Do not trust a bare `confirmed:true` or `status` parameter. First prepare a publish preview; then commit only after teacher confirmation is cryptographically/session bound to exam ID, draft version/content hash, batch, schedule and intended side effects.

Output: `{success, examId, status, examUrl?}`. `examUrl` only if generated by the trusted Abhyas service. Notifications disabled by default in demo mode and require separate human approval for real cohorts.

## Stable errors

`UNAUTHENTICATED`, `FORBIDDEN`, `BATCH_NOT_FOUND`, `BATCH_AMBIGUOUS`, `INVALID_SCHEDULE`, `INVALID_MARKING_SCHEME`, `DRAFT_NOT_FOUND`, `DRAFT_NOT_EDITABLE`, `QUESTION_VALIDATION_FAILED`, `QUESTION_COUNT_SHORTFALL`, `MODEL_RATE_LIMITED`, `MODEL_TIMEOUT`, `IDEMPOTENCY_CONFLICT`, `CONFIRMATION_REQUIRED`, `CONFIRMATION_STALE`, `PUBLISH_FAILED`.

## Invariants

- `duration` and `targetQuestions` are positive integers; `defaultMarks` 1–20.
- `negativeMarks` between zero and marks; negative rule must be from allowed enum.
- Date/time parsed in explicitly resolved institute timezone; start < end; window >= duration.
- Question count shortfall is surfaced, never hidden.
- MCQ option count 2–5 per supplied source guardrail; correct option must match a normalized option ID. Verify actual Abhyas support for 5 options.
- Mutations are idempotent; retries cannot create duplicate exams, question sets or assignments.
- Publication and notifications are separate side effects with explicit approval gates.
